   124→## Mobile Port Strategy
   125→
   126→The user asked about long-term mobile porting options. Here's the analysis:
   127→
   128→### Option A: PWA (Progressive Web App) — RECOMMENDED for launch
   129→- **What**: Add a web manifest + service worker to the existing Next.js app. Users "Install to Home Screen."
   130→- **Pros**: Zero code duplication. Same React/TS codebase. Works offline (matches design doc §12.1). No app store review. Instant updates.
   131→- **Cons**: Slightly slower than native. No App Store discoverability. iOS Push notifications limited.
   132→- **Effort**: ~2-3 days (manifest, service worker, install prompt, offline caching)
   133→- **Verdict**: Best first step. The design doc explicitly says "PWA: Offline support via service worker" (§12.1).
   134→
   135→### Option B: Capacitor (Ionic) — Best for App Store distribution
   136→- **What**: Wrap the existing Next.js web build in a native shell (Capacitor) that ships to iOS/Android app stores.
   137→- **Pros**: Same web codebase. Native app store presence. Access to native APIs (camera, haptics, push). Better performance than PWA on iOS.
   138→- **Cons**: Need to handle Next.js SSR → static export (or run a local server in the app). Build pipeline complexity.
   139→- **Effort**: ~1-2 weeks (Next.js static export config, Capacitor setup, native build/test)
   140→- **Verdict**: Best when you want app store presence without rewriting.
   141→
   142→### Option C: React Native — Only if you want truly native UX
   143→- **What**: Rewrite the UI in React Native (shared game logic in TS, different components).
   144→- **Pros**: Truly native performance and feel. Better animations. Full native API access.
   145→- **Cons**: **Duplicate UI codebase**. The game logic (data/, state/, logic/) can be shared 1:1, but every component must be rewritten. Significant ongoing maintenance.
   146→- **Effort**: ~4-8 weeks for full feature parity
   147→- **Verdict**: Only worth it if mobile is a primary platform and PWA/Capacitor feel isn't good enough. For an idle game (mostly text, numbers, progress bars), PWA is usually sufficient.
   148→
   149→### Option D: Expo (React Native simplified) — Middle ground
   150→- **What**: Use Expo to build a React Native app with web target. Share game logic, write native components.
   151→- **Pros**: One codebase for iOS + Android + web. Expo handles native build complexity.
   152→- **Cons**: Still need separate components from the web app. Performance overhead for complex state.
   153→- **Effort**: ~3-6 weeks
   154→- **Verdict**: Good if you want native + web from one project, but requires component rewrite.
   155→
   156→### Recommendation
   157→1. **Now**: Ship as PWA (2-3 days work). The game is already mobile-responsive.
   158→2. **If app store presence needed**: Wrap with Capacitor (1-2 weeks).
   159→3. **Only if native performance is critical**: Consider React Native/Expo (4-8 weeks, shared logic only).
   160→
   161→The current Next.js codebase is already structured to support this path: all game logic is in `src/game/` (framework-agnostic TS), and all UI is in `src/components/game/`. The logic layer can be imported into any React framework without changes.

  1156→## Design rationale for the reveal rule
  1157→
  1158→The task spec says "If the player has NEVER locked an archetype (i.e., it's not in `archivedArchetypes`), show ???". The reveal helper therefore treats the currently-locked archetype as known: `isArchetypeKnown = archivedArchetypes.includes(id) || lockedArchetype === id`. This way:
  1159→- First time locking X (this run): name shown throughout the run (player gets feedback on their choice).

  1282→## Design Decisions / Notes
  1283→
  1284→1. **Mastery bonus is generic, not per-type**: The `ChallengeDef.mastery.bonus` interface matches the achievements pattern (`{ type: "production" | "manual" | "capacity" | "evolve"; value: number }`). All 10 challenges grant a `production`-type bonus, so they all stack into the production multiplier (alongside achievements). The user-facing labels ("+10% food production", "+10% pop growth", "+15% starting resources") are aspirational flavor text rather than mechanically distinct bonuses — implementing them as truly per-resource bonuses would require additional multipliers in tick() for each resource, which is out of scope for this task. The mastery bonus is added to `techMultiplier()` so it benefits ALL production (systems, manual actions, etc.).
  1285→
  1286→2. **Challenge persists through stage evolve**: A challenge started in Cell stage carries through to Tribal, Civilization, etc. — the debuff applies for the entire run until the objective is met. This is intentional: it makes long-objective challenges (e.g., lateStage_challenge requiring Galactic) feasible.
  1287→
  1288→3. **Challenge does NOT persist through prestige**: `initialRunState()` resets `activeChallenge: null` on every fresh run / prestige. This is intentional — challenges are single-run trials. Mastery rewards persist forever; the trials themselves are per-run.
  1289→
  1290→4. **Speed challenge uses run-time, not wall-clock**: The `clearCellFast` completion type uses `s.time - s.challengeRunStart` to compute elapsed game-time (not real time). This means the 8× speed boost actually helps, and offline progress simulation doesn't count against the timer. The 5-minute (300 second) threshold refers to game-time seconds at the current speed setting.
  1291→
  1292→5. **`zeroStart` keeps happiness at 5**: Zeroing all resources including happiness would make the run dead-on-arrival (pop growth heavily penalized at happiness < 40). The challenge keeps a minimal happiness baseline of 5 so the run is hard but not impossible.
  1293→
  1294→6. **`forcedArchetype` immediately locks the lineage**: For the archetype_challenge, the player is locked to Reptilian at challenge-start (no Creature→Tribal drift). This requires the player to start in a stage where they can survive as Reptilian — they'd typically start the challenge at Cell stage and the lineage is locked from the start.
  1295→
  1296→7. **Story popup priority on first Galactic win**: `evolution_layer_unveiled` takes priority over `god_opens_its_eyes` because the challenges layer is more contextually relevant (the player has just unlocked a new system). On subsequent prestige (non-Galactic), no popup fires (consistent with previous behavior). On subsequent Galactic wins, no popup fires (the unlock already happened).
  1297→
  1298→8. **No new achievements**: Adding challenge-specific achievements (e.g., "Master 5 challenges") would be a natural extension but is out of scope for this task. The existing achievement framework supports it — a future task could add 3-5 challenge-specific achievements to the `ACHIEVEMENTS` array.

  1384→## Design Decisions
  1385→
  1386→1. **Prestige layer data is informational only**. As the task spec said, the data documents the full progression arc but does NOT implement the mechanics. The only layer currently mechanically wired is Evolution (Layer 1) — handled by the Challenges system from Task 7. Future tasks should reference `PRESTIGE_LAYER_MAP` for layer order, currency names, and unlock gates when implementing subsequent layers.
  1387→
  1388→2. **Resource naming is COSMETIC ONLY**. Resource IDs are unchanged. The save state, all costs, all production logic, all achievements, all challenges use the canonical ids (`glucose`, `atp`, etc.). Only the human-readable display name changes. This means: a Necroid save and a Lithoid save are 100% interoperable at the data layer.
  1389→
  1390→3. **Scope of renamed resources is intentionally narrow**. Only Cell and Creature stage resources are renamed (11 total). By Tribal, civilization has organized around its lineage's biology and civic terms (Wood, Stone, Science, etc.) standardize across all archetypes. This mirrors real-world etymology — biology shapes earliest vocabulary, but civic life converges on shared bureaucratic terms. It also keeps the naming overhead bounded: a future task that wants to rename later-stage resources can extend `RENAMEABLE_RESOURCES` without touching the existing 11.
  1391→
  1392→4. **Humanoid drift is minimal but non-zero**. The 13 archetypes include "humanoid" as the standard/default. Naming its resources identically to the defaults would make a humanoid run feel like the naming system isn't doing anything. Instead, humanoid gets slightly more grounded variants ("Vital Energy", "Sugar", "Rations", "Fresh Water", "Records") that signal "this is the human baseline" without breaking the cosmetic flavor.
  1393→
  1394→5. **Helper signature: `resourceName(id, archetypeId?)` with optional second arg**. The parameter is optional so existing callers don't break. Callers that don't pass it get the default name; callers that pass `lockedArchetype` get the archetype-flavored name. This makes the migration trivially incremental.
  1395→
  1396→6. **No state/store migration needed**. The new files are pure data + helper functions. They don't touch `GameState`, `GameStore`, the save format, or the tick loop. Old saves load identically. The `lockedArchetype` field (already in state from Task 1) is the only state the new feature reads.

  1662→## Design Decisions
  1663→
  1664→1. **Indirect mutual-exclusivity for ascension spires**. The `SystemDef` interface has no `exclusiveWith` field (only `TechDef` does). To make the three ascension spires mutually exclusive, I used `requiredTech` — each spire requires its respective ascension tech (`biological_ascension`, `synthetic_ascension`, `psionic_ascension`), and since those techs are already a 3-way exclusive path, exactly one spire variant is ever buildable per run. This required no changes to the SystemDef type, the store, or the UI — `requiredTech` is already wired up in `buySystem()` (store.ts:369) and the SystemsTab shows a red "Locked / Requires tech: X" badge.
  1665→
  1666→2. **Capacity-boosting systems scale upward across stages**. New capacity systems per stage: Civilization 1 (harbor), Empire 4 (railway_network, assembly_line, hospital, steel_mill), Solar 4 (space_station, lunar_base, asteroid_mining_station, habitat_ring), Galactic 3 (ftl_drive_array, wormhole_stabilizer, sentry_array). Total: 12 new capacity-boosting systems, complementing the 25 that already existed. Empire and Solar each got 4 because their primary resources (gold/production for Empire; energy/alloys for Solar) are heavily produced in those stages and need expanded caps to keep the loop flowing.
  1667→
  1668→3. **grantsAffinity density scales with stage complexity**. Cell: 13 systems with affinity (existing). My additions: Civilization 4/4 (all have affinity), Empire 7/8 (railway_network is the only one without — it's pure logistics), Solar 9/13, Galactic 14/18. Galactic has fewer-per-system because the cap is meaningful — the galactic_wonder, matter_decompressor, ftl_drive_array, wormhole_stabilizer, space_station, lunar_base, fusion_reactor, habitat_ring are concept-neutral infrastructure and don't push any single archetype.
  1669→
  1670→4. **Ascension preludes (`psionic_theory`, `synthetic_evolution`, `biological_mastery`) are NOT chained into `ascension_theory`**. They are tier-1 standalone techs that flavor the player toward a path before the formal ascension choice. A player can take all three preludes and then choose any of the three ascension paths — the preludes grant archetype drift but don't lock anything. This gives players more rope to explore the ascension theme before committing.
  1671→
  1672→5. **Galactic Governance is a SECOND 3-way exclusive path for the Galactic stage**, distinct from the ascension paths. This means a Galactic run now has TWO major mutually-exclusive choices: ascension (biological/synthetic/psionic) AND governance (federation/hegemony/alliance). The two paths are orthogonal — e.g. a player could choose Psionic Ascension + Imperial Hegemony (necroid-flavored psionic tyrant) or Synthetic Ascension + Free Worlds Alliance (arthropoid-flavored cybernetic merchant). This dramatically increases end-game replayability.
  1673→
  1674→6. **Tech tiers within each stage remain sane**. New techs honor the existing tiering convention: tier 1 (foundational, no requires), tier 2 (req a tier-1), tier 3 (req a tier-2). Galactic Governance (tier 3) requires `galactic_diplomacy` (tier 1), which requires `galactic_council` (existing tier 1) — a clean 3-step chain. dyson_sphere_tech (tier 3) requires `megastructure_construction` (existing tier 2), which requires `stellar_engineering` (existing tier 1).
  1675→
  1676→7. **All new IDs unique, all requires/exclusiveWith point at real tech IDs**. Verified via simulation script (see Verification). No conflicts with the existing 88 systems or 97 techs.
  1677→
  1678→8. **`university` (system) vs `universities` (tech)** — both existed conceptually. The Civilization tech `universities` (the technology) was already in techs.ts; my new `university` system is the physical building. Different IDs, different stages of abstraction. Same for `academy` (existing civ system) → `university` (new civ system, higher tier, more expensive). Library → Academy → University forms a 3-step science progression within the civ stage.
  1679→
  1680→9. **`steam_power` already existed as a Civilization tech** — to avoid name collision and confusion, my Empire-tier "Steam Power" themed tech is named `steam_mechanization`. Similarly `dyson_swarm` (existing Solar tech) vs my new `dyson_swarm_module` (Solar system) and `dyson_sphere_tech` (new Galactic tech that builds on the existing `dyson_sphere` system). The naming is intentional to keep IDs distinct without confusing players.

  1925→## Design Rationale
  1926→
  1927→1. **Why bump exclusive-path multipliers but not increase their costs?** Exclusive techs already cost the same as non-exclusive peers of the same tier — the opportunity cost of locking out the other 2 paths IS the cost. The reward should be at least +30% to make the choice feel meaningful. A 10-15% bonus for permanently giving up 2/3 of the branch options was not a real choice.
  1928→
  1929→2. **Why reduce production rather than increase baseCost for solar/galactic?** The baseCosts are already gated by precursor resources (e.g., solar systems cost energy + alloys, which require building up solar infrastructure first). Increasing baseCost would gate these systems behind even more grinding. Reducing production keeps the systems accessible while slowing the late-game acceleration.
  1930→
  1931→3. **Why increase upkeep rather than reduce production to fix the upkeep ratio?** The 2-3x guideline is a ratio rule. Both options work mathematically, but increasing upkeep is more thematically appropriate (e.g., a fusion reactor that consumes 0.2 alloys/s when producing 15.0 energy/s is unrealistic — it should burn through more fuel). It also creates a more interesting decision: the player has to balance resource production to feed their reactors.
  1932→
  1933→4. **Cross-stage 50% production** is already implemented in `store.ts:153` (`stageMult = sys.stage === STAGES[s.stageIndex].id ? 1 : 0.5`). Earlier-stage systems continue to produce at half-rate in later stages, keeping all 131 systems relevant throughout a run. No changes needed here.
  1934→
  1935→5. **`food` is in STAGE_RESOURCES for every stage from creature onward** (creature, tribal, civilization, empire, solar, galactic). The cross-stage economy is healthy: food is produced by `grazing_grounds` (creature), `farm` (tribal), `harbor` (civ), `colony_ship` (solar), `terraformer` (solar), `ring_world` (galactic). No changes needed.

  1946→1. **Payback time still below 30s for many solar/galactic systems.** After changes, the average first-purchase payback for solar systems is ~8s and for galactic systems is ~7s.
