   124→## Mobile Port Strategy
   125→
   126→The user asked about long-term mobile porting options. Here's the analysis:
   127→
   128→### Option A: PWA (Progressive Web App) — RECOMMENDED for launch
   129→- **What**: Add a web manifest + service worker to the existing Next.js app. Users "Install to Home Screen."
   130→- **Pros**: Zero code duplication. Same React/TS codebase. Works offline (matches design doc §12.1). No app store review. Instant updates.
   131→- **Cons**: Slightly slower than native. No App Store discoverability. iOS Push notifications limited.
   132→- **Effort**: ~2-3 days (manifest, service worker, install prompt, offline caching)
   133→- **Verdict**: Best first step. The design doc explicitly says "PWA: Offline support via service worker" (§12.1).
   134→
   135→### Option B: Capacitor (Ionic) — Best for App Store distribution
   136→- **What**: Wrap the existing Next.js web build in a native shell (Capacitor) that ships to iOS/Android app stores.
   137→- **Pros**: Same web codebase. Native app store presence. Access to native APIs (camera, haptics, push). Better performance than PWA on iOS.
   138→- **Cons**: Need to handle Next.js SSR → static export (or run a local server in the app). Build pipeline complexity.
   139→- **Effort**: ~1-2 weeks (Next.js static export config, Capacitor setup, native build/test)
   140→- **Verdict**: Best when you want app store presence without rewriting.
   141→
   142→### Option C: React Native — Only if you want truly native UX
   143→- **What**: Rewrite the UI in React Native (shared game logic in TS, different components).
   144→- **Pros**: Truly native performance and feel. Better animations. Full native API access.
   145→- **Cons**: **Duplicate UI codebase**. The game logic (data/, state/, logic/) can be shared 1:1, but every component must be rewritten. Significant ongoing maintenance.
   146→- **Effort**: ~4-8 weeks for full feature parity
   147→- **Verdict**: Only worth it if mobile is a primary platform and PWA/Capacitor feel isn't good enough. For an idle game (mostly text, numbers, progress bars), PWA is usually sufficient.
   148→
   149→### Option D: Expo (React Native simplified) — Middle ground
   150→- **What**: Use Expo to build a React Native app with web target. Share game logic, write native components.
   151→- **Pros**: One codebase for iOS + Android + web. Expo handles native build complexity.
   152→- **Cons**: Still need separate components from the web app. Performance overhead for complex state.
   153→- **Effort**: ~3-6 weeks
   154→- **Verdict**: Good if you want native + web from one project, but requires component rewrite.
   155→
   156→### Recommendation
   157→1. **Now**: Ship as PWA (2-3 days work). The game is already mobile-responsive.
   158→2. **If app store presence needed**: Wrap with Capacitor (1-2 weeks).
   159→3. **Only if native performance is critical**: Consider React Native/Expo (4-8 weeks, shared logic only).
   160→
   161→The current Next.js codebase is already structured to support this path: all game logic is in `src/game/` (framework-agnostic TS), and all UI is in `src/components/game/`. The logic layer can be imported into any React framework without changes.

  1078→## Design Decisions
  1079→- **Additive scaling (linear)** over exponential: `1 + k * n` rather than
  1080→  `(1+k)^n`. At repeat 5 with `k=0.20`, additive gives 2.0× while exponential
  1081→  would give ~2.49×. Additive keeps the late-repeat curve bounded and more
  1082→  predictable for balance — at max repeat 4 (without upgrade), the worst
  1083→  debuff (Trial of Weakness, −60%) reaches −108% (i.e. full shutdown),
  1084→  which is the design-intended "this is the hardest you can push it".
  1085→  Players who want to go further need the `challenge_mastery` upgrade.
  1086→- **Effect targets as plain strings**, not `ResourceId` union. Several
  1087→  challenge effects target derived handles (`"all_production"`,
  1088→  `"population_growth"`, `"caps"`, `"starting_pop"`) that aren't real
  1089→  resources. Using `string` keeps the type open without `as any` casts in
  1090→  the game loop. The set of valid targets is documented in the
  1091→  `ChallengeEffect` JSDoc block.
  1092→- **Two aggregation functions** (`challengeMasteryBonus` vs
  1093→  `challengeMasteryBonusFromRepeats`): the first assumes 1 completion per
  1094→  challenge (base mastery only); the second properly stacks across repeats.
  1095→  The split lets the UI show "potential mastery if you complete everything"
  1096→  without committing to a specific repeat-count state.
  1097→- **Deep-cloning** in `getChallengeDebuffAtRepeat` / `getChallengeMasteryAtRepeat`:
  1098→  returns new arrays/objects with scaled values so callers can safely mutate
  1099→  without corrupting the canonical `CHALLENGES` definitions.
  1100→- **No state changes**: neither file touches `types.ts`, `store.ts`, or any
  1101→  existing data file. The two new files are pure data + pure functions, so
  1102→  they cannot introduce regressions into the existing game loop.

  1348→## Design Decisions
  1349→- **`challengeMasteryBonusFromRepeats` over `challengeMasteryBonus`** in
  1350→  `techMultiplier` and `triggerPrestige`. The non-repeats version assumes 1
  1351→  completion per challenge (base mastery only), which under-credits players
  1352→  who have repeated a challenge 3-5×. The `FromRepeats` version properly
  1353→  sums the base + (1 + 0.50*i) for each repeat, so repeat 3 of Trial of
  1354→  Famine grants +0.20 + 0.30 + 0.40 = +0.90 to food mastery.
  1355→- **Per-resource challenge mult** applied INSIDE the system production loop
  1356→  (per `[r, v] of Object.entries(produces)`), not as a global multiplier.
  1357→  This is important because the production loop iterates over multiple
  1358→  resources per system — a single food-debuff challenge (Trial of Famine)
  1359→  should only nerf the `food` output, not the `water` or `organic_matter`
  1360→  outputs of the same system.
  1361→- **Cap debuff applied AFTER `recomputeCapacitiesFresh`** rather than as
  1362→  part of the `capMult + archCapMult` argument. This is because the cap
  1363→  debuff is a runtime conditional (only when `s.activeChallenge` is set),
  1364→  while the `capMult` argument is the always-on vault/archetype bonus.
  1365→  Mixing them would have meant always paying the cost of a conditional
  1366→  branch in the inner loop. Cleaner to post-multiply.
  1367→- **`autoEvolveTrigger` deferred until AFTER the tick's `set()`**:
  1368→  `evolveStage()` itself calls `get()` then `set()`. If we called it before
  1369→  committing the current tick's state, the evolve would read stale data
  1370→  (e.g. the auto-buyer just-purchased systems wouldn't be in state yet).
  1371→  By deferring, the evolve correctly sees the freshly committed population,
  1372→  systems, tech, and score.
  1373→- **`flat` challenge effects only at run start**: Trial of the Late Bloom
  1374→  uses `{ target: "starting_pop", mode: "mult", value: -0.50 }` and Trial of
  1375→  Growth's mastery uses `{ target: "starting_pop", mode: "flat", value: 10 }`.
  1376→  Both are applied inside `triggerPrestige()` against the fresh
  1377→  `initialRunState()`, NOT inside the tick loop. Otherwise the debuff would
  1378→  re-apply every tick and the player's population would crash to 1
  1379→  instantly.
  1380→- **Auto-Evolver threshold 100% + level×20%**: at level 1, the player must
  1381→  hit 120% of evolve requirements; at level 5, 200%. This means Auto-Evolver
  1382→  isn't a free pass — it only fires when the player is comfortably past the
  1383→  requirements (and could evolve manually anyway). It saves the click, not
  1384→  the gameplay.

  1412→  challenges whose mastery has `mode: "mult"` (e.g. +15% food production),
