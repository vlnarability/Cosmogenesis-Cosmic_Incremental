  4171→### Design Decisions
  4172→- **File named `divinity_layer.ts`, not `divinity.ts`.** The `divinity`
  4173→  string is already a `ResourceId` in `resources.ts` and `types.ts`.
  4174→  Naming the module `divinity.ts` would have shadowed the resource id
  4175→  in import paths and created ambiguity (does
  4176→  `import { divinity } from "./divinity"` refer to the layer or the
  4177→  resource?). The `divinity_layer.ts` name sidesteps the collision
  4178→  while preserving the Layer 8 identity; the exported constants use
  4179→  the bare prefixes (`PRAYER_CHANNELS`, `DIVINE_MASKS`, etc.)
  4180→  consistent with the precedent set by `apotheosis.ts` (`DIVINE_LAWS`,
  4181→  not `apotheosis_laws`).
  4182→- **Prayer Channels are NOT one-per-run.** The task spec wording "6
  4183→  Prayer Channels — route prayer output into different divine effects"
  4184→  describes six parallel conduits the player invests prayer into, not
  4185→  a single-choice like Divine Masks. The completion check requires
  4186→  opening 3, which would be impossible if channels were mutually
  4187→  exclusive. The "pick" is which to LEVEL (and how high), not which
  4188→  to ENABLE — mirrors the Logic Cores pattern (`installedCores` is a
  4189→  set, not a single id).
  4190→- **Channels use `*PerLevel` field names (not the bare mult names).**
  4191→  Distinguishes the per-level magnitude from the aggregate bonus. The
  4192→  Def has `populationGrowthMultPerLevel: 0.10`; the Bonus has
  4193→  `populationGrowthMult: 0.30` (at level 3). This naming makes the
  4194→  relationship between the two layers of data explicit and matches
  4195→  the singularity.ts `divinityPerSec` (flat) vs `divinityPerSecPerLevel`
  4196→  (per-unit) precedent.
  4197→- **Wealth Channel sets BOTH `goldMultPerLevel` AND `productionMultPerLevel`.**
  4198→  The spec wording "+15% gold/production per prayer level" parses as a
  4199→  paired effect on a single channel, not two separate channels. The
  4200→  IIFE validator's "each channel sets at least one effect" rule is
  4201→  satisfied; the paired effect is intentional.
  4202→- **Divine Masks and Worship Polarities return aggregates, not Defs.**
  4203→  Mirrors the more recent precedent (`omnipotence.ts hybridBonus` /
  4204→  `singularity.ts relicBonus`) over the older one (`apotheosis.ts
  4205→  worshipModeBonus` returns the Def directly). Aggregate return type
  4206→  gives cleaner consumer code: `const m = divineMaskBonus(state.activeMask);
  4207→  production *= (1 + m.productionMult)` — no null-check needed.
  4208→- **`divinityMult` defaults to 0 (additive), not 1 (multiplicative).**
  4209→  The consumer multiplies Divinity gains by `(1 + divinityMult)`, so
  4210→  the additive identity (0) maps to "no change" (×1.0). This matches
  4211→  `productionMult` / `militaryMult` / etc. semantics. The Sage's +0.50
  4212→  means ×1.5 Divinity. Contrast with `happinessDrainMult` on
  4213→  `WorshipPolarityBonus`, which defaults to 1.0 because it's
  4214→  multiplicative (drain × 1.0 = unchanged). The split mirrors the
  4215→  apotheosis.ts `DivineLawBonus` (which has additive `productionMult`
  4216→  defaulting to 0 alongside multiplicative `worshipMult` defaulting
  4217→  to 1).
  4218→- **Worship Polarity names intentionally overlap with apotheosis.ts
  4219→  Worship Modes.** Layer 8 is the apotheosis-era "Worship Modes" idea
  4220→  refined — a Divinity-layer god is choosing the *polarity* of its
  4221→  worship, not the mode. Effects overlap by design (Reverence in both
  4222→  layers boosts production; Fear in both layers halves happiness drain
  4223→  + boosts military). Stacking the two layers compounding bonuses is
  4224→  intended progression, not a bug.
  4225→- **`isDivinityComplete` accepts a Record + string|null signature.**
  4226→  Mirrors `isSingularityComplete(installedCores, compressionPerformed)`
  4227→  and `isApotheosisComplete(lawsCodified, heresySchismResolved)`. The
  4228→  two conditions (≥3 channels opened AND a polarity aligned) each map
  4229→  to one argument, keeping the function signature readable.
  4230→- **Channel "open" check is `level >= 1`, not `level > 0`.** Equivalent
  4231→  for positive integers but more explicit about the semantic ("a channel
  4232→  is opened when at least 1 level has been invested"). A channel
  4233→  absent from the map is treated as level 0 (unopened), via
  4234→  `channels[c.id] ?? 0`.
  4235→- **The Faith Channel's `divinityPerSecPerLevel: 0.01` is a flat grant,
  4236→  not a mult.** The consumer adds this directly to
  4237→  `state.resources.divinity` per second. This is the only channel that

  4411→### Design Decisions
  4412→
  4413→- **Echo `bonus` is a nested object, not flat fields on the echo def.**
  4414→  The spec wording "each echo has: id, name, desc, icon, bonus, cost
  4415→  (in Echoes currency)" calls out `bonus` as a distinct field. The
  4416→  `EchoBonusFields` sub-object keeps the per-echo effect separate
  4417→  from the metadata fields and the cost, making `echoBonus` iterate
  4418→  `echo.bonus.productionMult` instead of `echo.productionMult`. This
  4419→  reads cleanly at the call site and matches the spec's shape
  4420→  exactly. Contrast with `DivineLawDef` in `apotheosis.ts`, where the
  4421→  bonus fields are flat on the def — that file's spec didn't call out
  4422→  a `bonus` sub-object.
  4423→
  4424→- **Echoes are ownable multiple times; `echoesOwned` is
  4425→  `Record<string, number>`.** The spec wording "completed runs leave
  4426→  behind echoes" implies echoes accumulate across runs (persistent,
  4427→  not per-run). Modeling the ownership as a count (not a boolean set)
  4428→  supports the natural design of "owning 3 Growth Echoes for +30%
  4429→  pop growth" and matches the player expectation that completing more
  4430→  runs of the same type yields more of that echo. The `echoBonus`
  4431→  function multiplies each echo's `bonus` fields by the count owned
  4432→  and sums — 6 echoes × arbitrary counts is O(6) per tick, cheap.
  4433→
  4434→- **`forkBonus` returns the bonus for ONE fork (not the aggregate
  4435→  across all forks).** The signature `forkBonus(forkId, branch)` is
  4436→  spec'd; the consumer (store) iterates `FORK_SCENARIOS` and calls
  4437→  `forkBonus` per resolved fork if it wants the run-wide aggregate.
  4438→  This mirrors the precedent that `relicBonus` /
  4439→  `worshipModeBonus` / `divineMaskBonus` return the bonus for a single
  4440→  pick (not an aggregate over many) — the per-fork design preserves
  4441→  that shape even though multiple forks can be resolved in one run.
  4442→  The store wiring task will provide a `allForkBonuses(state.forksResolved)`
  4443→  aggregate if the tick loop needs it.
  4444→
  4445→- **`epMult` lives on `ForkBranchDef`, NOT on `EchoBonusFields`.** EP
  4446→  (Evolution Points) is the Layer 1 prestige currency; boosting it is
  4447→  a capstone decision gated behind The Final Divergence fork
  4448→  (branch A, +100% EP). Echoes never grant EP multipliers — only
  4449→  production / growth / military / science / gold / caps / happiness
  4450→  / Divinity. This keeps the EP economy gated behind a single,
  4451→  deliberate late-run choice, matching the spec wording "choose
  4452→  between +100% EP OR unlock a random divine law for free".
  4453→
  4454→- **`ForkSpecial` discriminated union (modeled on
  4455→  `singularity.ts RelicSpecial`).** The Final Divergence branch B's
  4456→  "unlock a random divine law for free" is a one-time action, not a
  4457→  flat stat bonus — it can't fit in the mult-field shape. The union
  4458→  has a single variant `{ kind: "unlock_random_divine_law" }` today
  4459→  (no parameters — the consumer picks the law from
  4460→  `apotheosis.ts DIVINE_LAWS` at random). The IIFE validator
  4461→  exhaustively switches on `special.kind` so adding a new variant in
  4462→  the future is type-checked. This pattern is the established one for
  4463→  "special interaction" mechanics in this codebase.
  4464→
  4465→- **`isInfinityComplete(forksResolved, debtRepaid)` mirrors the
  4466→  `isSingularityComplete(installedCores, compressionPerformed)`
  4467→  precedent.** Two args: a Record + a boolean. The first condition
  4468→  (at least 1 fork resolved) checks engagement with the Forks
  4469→  mechanic; the second (a debt repaid) checks the player survived a
  4470→  complete boost + penalty cycle on any Future Debt tier. The
  4471→  "resulting" in the spec wording "Fork a timeline and repay the
  4472→  resulting Future Debt" is interpreted loosely as "any Future Debt
  4473→  taken during the run" — mechanically, the Future Debt family is
  4474→  not directly tied to forks (the spec lists them as separate
  4475→  families), so the completion check accepts any repaid debt.
  4476→
  4477→- **Future Debt `penaltyMult` is always negative.** The IIFE
  4478→  validator enforces `penaltyMult < 0` — a penalty that's >= 0 would
  4479→  make the debt free, breaking the "borrow strength now, pay back
  4480→  later" theme. `boostMult` is always > 0 (the whole point of debt is
  4481→  to borrow strength). `boostMult` is additive on production (the
  4482→  consumer multiplies by `(1 + boostMult)`), so +50% = 0.50, +500% =
  4483→  5.00. The validator also enforces both durations > 0 and
  4484→  `perRunLimit >= 1`.
  4485→
  4486→- **`echoesOwned` is persistent across runs (file header comment
  4487→  documents this).** Unlike `forksResolved` / `activeFutureDebt` /
  4488→  `futureDebtUses` which are per-run, echoes are the persistent
  4489→  reward for completing Infinity-layer runs — owning 3 Growth Echoes
  4490→  means every subsequent run gets +30% pop growth from the start.
  4491→  This matches the spec wording "completed runs leave behind echoes
  4492→  that provide passive bonuses" and the `persistentReward` field on
  4493→  `prestigeLayers.ts infinity`: "Each repaid Future Debt grants a
  4494→  permanent +5% production bonus" — both echoes and repaid debts
  4495→  persist.

  4497→### Unresolved Issues / Risks
  4498→
  4499→1. **No Echoes-currency earn rate defined.** The file declares the
  4500→   Echo Type `cost` field (in Echoes currency) but not how Echoes are
  4501→   earned at prestige. The wiring task should pick a formula (e.g.
  4502→   `echoesEarned = floor(forksResolvedCount × 2 + debtsRepaidCount × 3)`)
  4503→   so the first Infinity-layer prestige grants ~5 echoes (enough for
  4504→   one cheap echo). Without this, the player has no way to buy echoes.
  4505→
  4506→2. **No cost scaling for subsequent echo copies.** The file declares
  4507→   a flat `cost` per echo type — the first copy costs that much, but
  4508→   the spec doesn't say how the second copy scales. The natural
  4509→   design is `cost × (1 + count_owned)` (linear scaling) or
  4510→   `cost × 2^count_owned` (exponential). Linear is more forgiving;
  4511→   exponential matches the prestige-game convention. The wiring task
  4512→   should pick one and apply it in the store's `buyEcho` action.
  4513→
  4514→3. **Fork resolution is per-run, but the spec doesn't say whether a
  4515→   resolved fork can be un-resolved.** The cleanest design is
  4516→   one-shot per run (once you pick Crossroads branch A, you can't
  4517→   switch to branch B without prestiging). The wiring task should
  4518→   make `forksResolved` effectively immutable within a run (no
  4519→   `unresolveFork` action). If a "Fork Reset" upgrade is desired
  4520→   later (e.g. from a future Future Debt interaction), it should
  4521→   explicitly clear the entry rather than mutate it.
  4522→
  4523→4. **The Future Debt timer mechanic isn't fully spec'd here.** The
  4524→   file declares the per-tier `boostDuration` / `penaltyDuration` /
  4525→   `perRunLimit` but the actual timer state (`activeFutureDebt`,
  4526→   `futureDebtPhase`, `futureDebtTimer`) is left to the wiring task
  4527→   (documented in the file header comment). The tick loop must
  4528→   decrement `futureDebtTimer` each second, transition
  4529→   `"boost"` → `"penalty"` when the boost expires, and clear the
  4530→   active debt (setting `futureDebtRepaid = true`) when the penalty
  4531→   expires. Stacking is intentionally NOT supported (`activeFutureDebt`
  4532→   is a single id, not a set) — invoking a new debt while one is
  4533→   active should either be blocked or replace the current one
  4534→   (wiring task's choice; blocking is safer).
  4535→
  4536→5. **The Final Divergence branch B's `unlock_random_divine_law`
  4537→   special needs a defined "random" source.** The spec wording is
  4538→   "unlock a random divine law for free" — the consumer should pick
  4539→   from `apotheosis.ts DIVINE_LAWS` (8 entries) either truly at
  4540→   random or from a curated subset (e.g. only laws the player hasn't
  4541→   codified this run). The wiring task should also decide whether
  4542→   this special can fire if all 8 laws are already codified (probably
  4543→   no-op with a notification, but worth confirming).
  4544→

  4724→### Design Decisions
  4725→
  4726→- **The Clause of Unity uses `allBonusesMult`, NOT a flat per-stat
  4727→  bonus.** The spec wording "all bonuses +25%" is ambiguous between
  4728→  (a) +25% to all OTHER accumulated bonuses (META-amp), and (b) +25%
  4729→  to all stats (flat per-stat). I chose (a) because (i) it's thematically
  4730→  richer — Unity amplifies everything the god has built across all 10
  4731→  layers, not just the base stats; (ii) it makes Unity the capstone
  4732→  clause (the most expensive at cost 25, ~5× the next-priciest), since
  4733→  its value scales with everything else the player owns; (iii) the
  4734→  validator's "exactly one effect field" rule would be impossible to
  4735→  enforce if Unity had 7 separate per-stat fields. The consumer applies
  4736→  `allBonusesMult` LAST in the bonus aggregation pipeline — applying it
  4737→  per-source would compound it incorrectly.
  4738→
  4739→- **The IIFE validator enforces EXACTLY ONE effect field per clause.**
  4740→  A clause that mixes `productionMult` (flat per-stat) with
  4741→  `allBonusesMult` (META-amp) would conflate two distinct design intents
  4742→  in a single entry. The validator rejects this — each clause is either
  4743→  a flat per-stat boon OR the META-amp, never both. This makes the
  4744→  clause's mechanical role unambiguous from its def.
  4745→
  4746→- **Canonization `kind` is a discriminated union, and the validator
  4747→  enforces kind-appropriate effect fields.** `story_beat` must set
  4748→  `productionMult` (and must NOT set `epFromStageMult`); `stage_clear`
  4749→  must set `epFromStageMult` (and must NOT set `productionMult`);
  4750→  `archetype` must set NEITHER (the bonus lives on the archetype def,
  4751→  and the consumer queries `ARCHETYPES[id].bonus` directly per canonized
  4752→  archetype id). This prevents data drift where a story-beat
  4753→  canonization accidentally grants EP, or an archetype canonization
  4754→  accidentally grants a flat production bonus that doesn't match the
  4755→  archetype's actual bonus shape.
  4756→
  4757→- **`canonizationBonus` does NOT aggregate archetype canonizations.**
  4758→  Archetype bonuses have a rich shape (per-resource production mults,
  4759→  all-production mult, pop-growth mult, cap mult — see
  4760→  `archetypes.ts ArchetypeDef.bonus`) that doesn't fit a flat
  4761→  `CanonizationBonus` object. The consumer iterates the
  4762→  `canonizedArchetypes` state map and queries each archetype's bonus
  4763→  directly. `canonizationBonus` only aggregates the flat per-purchase
  4764→  bonuses from story-beat and stage-clear canonizations. This mirrors
  4765→  the `forkBonus` precedent in `infinity.ts` (per-fork single-branch
  4766→  bonus, not aggregate-across-many) — the consumer composes aggregates
  4767→  itself when needed.
  4768→
  4769→- **Permanence Weaves grant NO stat bonus.** The weave's only effect is
  4770→  pinning an item across resets. The consumer queries the source
  4771→  definition (`DIVINE_LAWS` / `WORSHIP_MODES` / `ROUTES`) for the
  4772→  pinned item's bonus. This avoids duplicating the bonus shape (which
  4773→  would drift if the source def changed) and keeps the weave def
  4774→  minimal. The `PermanenceWeaveDef` has no bonus fields.
  4775→
  4776→- **The Cosmic Boon is LINEAR additive, not compounding.** The spec
  4777→  wording "stacks with each reset" is ambiguous between (a) linear
  4778→  stacking (+100% per stack × N stacks = +N×100%), and (b) compounding
  4779→  (×2 per stack × N stacks = ×2^N). I chose (a) because (i) compounding
  4780→  would make the boon trivialize the game after a few resets
  4781→  (×2^5 = ×32 production would obsolete every other system); (ii) linear
  4782→  stacking is more predictable and matches the precedent of all other
  4783→  additive multipliers in the codebase (echoes, divine laws, fork
  4784→  branches, etc.); (iii) the spec's three boon values (+100% production,
  4785→  +100% EP, +50% caps) are clearly per-stack values, and the natural
  4786→  reading is "N stacks × per-stack value". The `cosmicBoonBonus` helper
  4787→  multiplies the per-stack values by `stacks` directly — no
  4788→  compounding.
  4789→
  4790→- **`isEternityComplete` is trivially `endingChosen !== null`.** Unlike
  4791→  the Infinity layer (which gates on forks + debt repaid) or the
  4792→  Apotheosis layer (3+ laws + schism resolved), Eternity has no
  4793→  pre-requisite threshold — the player can choose an ending immediately
  4794→  upon reaching the layer. The richness comes from the PERMANENCE of
  4795→  the purchases (clauses, canonizations, weaves all persist forever),
  4796→  not from a gating threshold. A player who chooses Reset immediately
  4797→  forfeits the chance to spend Testament Clauses this run, which is
  4798→  its own soft gating.
  4799→
  4800→- **`cosmicBoonBonus` is exported as a 4th helper (BONUS).** The spec
  4801→  lists 3 required helpers (`testamentClauseBonus`, `canonizationBonus`,
  4802→  `isEternityComplete`), but the Cosmic Boon mechanic is described in
  4803→  detail in the spec and the consumer needs to compute it. Adding
  4804→  `cosmicBoonBonus` as a well-tested helper is safer than asking the
  4805→  consumer to inline `stacks × ENDING_CHOICE_MAP["reset"].cosmicBoonPerStack`
  4806→  (which is error-prone — easy to forget the null check on
  4807→  `cosmicBoonPerStack`, or to forget to handle `stacks <= 0`). The
  4808→  helper centralizes the logic. The spec lists REQUIRED exports; it
  4809→  doesn't forbid additional ones.
  4810→
  4811→- **The file exports `ENDING_CHOICE_MAP` and `_COUNT` constants beyond
  4812→  the spec's list.** Every other layer file (`apotheosis.ts`,
  4813→  `singularity.ts`, `omnipotence.ts`, `divinity_layer.ts`,
  4814→  `infinity.ts`) exports a `_MAP` for every list and a `_COUNT` for
  4815→  every list length. Eternity follows the same pattern for consistency.
  4816→  The consumer needs `ENDING_CHOICE_MAP["reset"]` to look up the
  4817→  Cosmic Boon per-stack values; without the map export, the consumer
  4818→  would have to `ENDING_CHOICES.find(e => e.id === "reset")` which is
  4819→  clunky and O(N).
